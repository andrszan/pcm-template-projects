# PCM 架构选型指南

## 目标

拿到客户需求后，从正式模板中分别选择能够满足硬性要求的最简单项目起点。AI 负责分析、说明理由和提供备选方案，最终决定由用户作出。

## 选型原则

1. 硬性要求优先于默认偏好。
2. `catalog.json` 是正式可选模板清单，也是选型阶段的唯一模板信息输入。
3. 前端、后端和其他项目起点根据各自约束独立选择，不因惯用搭配绑定无关技术。
4. 选择能够完成交付的最简单架构。
5. 不为尚未发生的假设性需求提前增加复杂度。
6. 没有合适的正式模板时必须明确说明，不把临时新建的架构描述成 PCM 正式模板。

## 业务范围判断

首先判断项目是否属于 PCM 当前阶段适合承接的范围。

通常可以考虑：

- Web 应用；
- 内容站点；
- 企业内部系统；
- 原型项目；
- 标准 API 服务。

通常需要谨慎判断或可能超出当前范围：

- 原生移动应用；
- 游戏；
- 强硬件依赖系统；
- 强算法项目；
- 需要生产级合规保障的受监管系统。

## 前端选型标准

### 目标平台

先确认目标属于以下哪种工程形态：

- Web/H5；
- 桌面应用；
- 移动应用；
- 小程序；
- 内容站点；
- 纯后端服务。

### 渲染和 SEO

- 明确要求 SEO 或服务端渲染：考虑支持 SSR/SSG 的模板。
- 不要求 SEO 的内部应用：通常使用 SPA 即可。
- 内容优先的官网、博客或文档站：优先考虑内容型架构。

### 界面特征

- 大量表格、表单、筛选器和树结构：优先选择面向企业中后台的组件体系。
- 强调自定义视觉或 AI/SaaS 产品体验：优先选择组合自由度更高的 UI 体系。
- 明确要求 Material Design：选择 Material 系组件体系。

### 部署和团队约束

必须尊重需求中明确提出的框架、部署平台、静态托管、浏览器运行环境和团队技术栈限制。

## 后端选型标准

### 是否需要后端

前端原型和静态内容站点可能不需要后端。需要数据库、业务 API 或服务端处理时，通常需要后端。

### 框架形态

- 标准独立 REST API：优先考虑 API 导向框架。
- 需要传统全功能框架或内置管理后台生态：考虑完整 Web 框架。
- 接口规模非常小：可以考虑轻量框架。

### 数据库与 I/O

- 只有明确需要持久化数据时，才选择包含 ORM 和迁移工具的模板。
- 普通 CRUD 不应仅因为“异步更先进”就选择复杂异步架构。
- 确实存在大量并发网络请求或外部服务调用时，再重点考虑异步 I/O。

### 语言、部署和团队约束

必须尊重需求中明确提出的语言、运行环境、数据库、部署平台和团队技术栈限制。没有硬性要求时，不因前端框架替用户绑定后端语言或数据库。

## 模板组合原则

正式模板是相互独立的项目起点，PCM 不维护预设技术组合。需要多个模板时，应按项目要求分别选择，不把历史惯用搭配当作优先级。

不同模板默认可以根据需求组合，但这不代表所有现在和未来的模板都无条件兼容。派生项目必须根据实际使用方式确认：

- 通信协议与数据格式；
- API 地址、环境变量和跨域策略；
- 认证、会话和安全边界；
- 文件上传、流式响应、WebSocket 等特殊能力；
- 本地开发、测试和部署拓扑。

发现真实的不兼容约束时，应说明具体限制并调整选型，不预先维护所有模板之间的兼容矩阵。

## 选型决策步骤

1. 判断项目的工程形态和硬性约束。
2. 读取 `catalog.json`，确定当前正式可选的项目起点。
3. 判断是否需要前端、后端或其他独立项目。
4. 程序按 `project_type` 区分前端与后端候选；比较时根据各候选模板的 `name` 和 `description` 判断工程形态与技术选型。
5. 为每个部分选择满足要求的最简单模板，并说明重要限制。
6. 如果正式模板无法满足要求，明确缺口并提出单独建议。

选型答复只需说明：

- 项目工程形态；
- 是否需要前端、后端或其他项目；
- 各部分推荐的模板；
- 推荐理由；
- 重要限制和派生验证事项。

不需要生成选型记录文件，也不在本仓库跟踪客户项目。

## 派生项目初始化

用户确认选型后，在独立的派生项目中：

1. 根据 `catalog.json` 中选定模板所属仓库的 `git_url` 和 `default_branch` 拉取仓库，并记录实际 commit SHA。
2. 根据模板的 `path` 将选定目录复制到派生项目，不直接在模板仓库中开发客户业务。
3. 根据已确认需求移除不需要的页面、依赖和基础设施。
4. 补齐项目实际需要的通信、环境变量、认证和部署配置。
5. 按模板 README 和依赖声明中的实际脚本执行安装、检查、测试和构建。
6. 存在多个项目时，验证关键接口、跨域、认证及本地联调等跨项目契约。
7. 完成初始化验证后，再进入正式功能开发。
